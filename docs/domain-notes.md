# Musical data and local storage

The domain model uses 480 integer ticks per quarter note and 1,920 ticks per 4/4 bar. The MVP supports 4/4 only; it is explicitly represented and validated, not implied by seconds. The default demonstration contains 16 bars at 86 BPM (approximately 44.65 seconds before an export tail). A new blank project starts at 90 BPM.

Tracks hold instruments, mixer settings, effects and clip instances. MIDI clips reference one shared source pattern. Duplicating a clip creates a new placement with a new clip ID and retains the pattern reference: editing the source updates every linked instance. Duplicating the pattern creates independent note and pattern IDs. Resizing a clip changes its playback window; with looping enabled, a source pattern repeats and is cut to that window. Notes store pitch, start, duration and linear velocity independently of UI state.

The Zustand store applies edits to a cloned project and keeps up to 80 prior snapshots for Undo/Redo. A new command after Undo discards redo history. Playback state, selection and audio nodes are excluded from saved musical data. Project replacement passes through schema validation and resets command history. The UI should commit a drag once, at pointer release, rather than making every pointer movement an undo entry.

Version 1 projects and imported audio Blobs are held in separate IndexedDB stores in `studio-local-v1`. Persistence resolves a write only after the transaction has committed. Project loading validates types, numeric ranges, timing, duplicate IDs and pattern references. Invalid or unsupported saved data raises a visible error and is never automatically overwritten or discarded. Missing audio binary data can be reported using `missingAssets`; metadata and the project remain recoverable. Deleting a project does not delete its assets because other projects may share them. Preferences and the most recently opened project ID may use localStorage via `readPreference` and `writePreference`; compositions never rely on localStorage.

Local inspiration is a seeded musical pattern generator, not a network AI model. Six categories yield three independent, validated alternatives and do not mutate the source project. Accepted suggestions use exactly the same editable MIDI model as manually authored notes. The provider interface anticipates a future server-side LLM integration. No key or external service is needed, and no secret belongs in frontend code.

The domain and persistence tests exercise a playable-length demo, tick/second conversion, pattern linkage, group edits, quantization boundaries, schema rejection, deterministic ideas, history branching, IndexedDB round trips and imported asset integrity.

There are currently no older project formats to migrate. Version 1 is the only accepted schema; a future version must introduce an explicit, tested migration before loading old data. Unknown top-level fields are rejected rather than silently stripped, and reference validation uses own properties to prevent inherited object keys from masquerading as stored patterns. A failed load/save never deletes the original IndexedDB entry. Imported asset retention is deliberate; future garbage collection must check every saved project and undo history before removing a blob.

Continuous controls can optionally call `update(label, mutator, { coalesceKey: 'track-id:volume' })`. Repeated changes to the same explicit key within 750 milliseconds share one undo entry. Loading, Undo, Redo, selection changes and unrelated commands break that group. Ordinary two-argument calls always preserve separate commands.
